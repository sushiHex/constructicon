## Authority and adjudications

This plan is subordinate to `docs/INVARIANTS.md`, `docs/ARCHITECTURE.md`, and
accepted ADRs. Where the historical plan no longer matches current truth, these
decisions apply.

1. **Close every mutation escape hatch, including trusted assembly.** I9, ADR
   0012, and the contributor command law are unconditional: registration and
   initial promotion cannot be exempt merely because only the trusted injection
   root calls them. Every run, approval, registration, promotion, and rollback
   mutation carries a transport-derived or launcher-minted static actor plus a
   caller idempotency key and enters one durable command session.
   The M5-era sentence that calls `system.start(graph, inputs)` a public execution
   surface is stale after M6 and is corrected in PR A. `Constructicon` keeps
   private domain verbs used by `ControlPlane`, plus nonmutating read/authoring
   operations (`validate`, `admit_graph`, and `describe`). Public `start`,
   `resume`, `reproduce`, `cancel`, `promote`, `rollback`, `prepare`,
   `run_prepared`, `register`, and `promote_initial` wrappers are removed rather
   than retained as a second control API.

   PR A adds local-only `registry_register` and `registry_promote_initial`
   ControlPlane methods. They require `auth_method="static"`, admin scope, and a
   caller key, but no MCP/HTTP/stdio tool exposes them. Registration keeps M2's
   exact component-hash idempotence and never moves a pointer. Initial promotion
   remains only the deterministic no-stable-pointer edge through the existing
   journal-minted policy attestation. A new ADR records why local availability is
   a transport boundary, not an exception to I9 or ADR 0012. `AGENTS.md`,
   architecture, and contributing guidance keep “every mutation” literal.
2. **Preserve PR #9's attempt fence.** A resume plan is not a generic
   `{run_id}` target. PR #9 persists `baseline_event_seq`; the plan schema binds
   the exact admissible-status policy `{PENDING, RUNNING, FAILED, PARKED}` rather
   than serializing an unordered status collection.
3. **Preserve durable rows.** Existing unversioned prepared plans and v1/v2
   committed responses remain readable in memory and are never rewritten merely
   because a command is replayed.
4. **Registry revisions are read cuts, not execution identity.** The revision
   pair makes queries reproducible. It does not enter component hashes, sealed
   manifests, world hashes, invocation ids, or effect ids.
5. **Cursor schema 1 is ephemeral.** M6.2 emits schema 2 and rejects old cursors
   with typed restart guidance. It does not migrate, sign, or persist them.
6. **SQLite movement is not a migration.** The database remains schema version 5;
   responsibility-based Python modules must not alter SQL, table names, durable
   rows, transaction boundaries, or migration behavior.
7. **Historical handoffs are not evidence.** Only merged code, tests, exact-head
   verification, and post-merge verification can close this plan.
8. **Canonical set ordering is an I13 correction, not an identity migration.**
   Already-retained component rows and hashes remain authoritative and
   byte-identical. Unaffected component definitions retain their existing hash
   fixtures. Only a newly computed definition whose former JSON depended on
   unordered `labels` or `change_surfaces` uses the sorted canonical bytes; an
   exact retained semantic definition is found and reused before any new hash is
   computed. Downstream identities newly derived from a corrected affected hash
   follow that hash; this is explicit, not hidden under a byte-identical claim.
   Fixtures pin retained/unaffected identity chains and affected definitions
   across distinct `PYTHONHASHSEED` processes.

# PR A — M6.1 command-law and lifecycle closeout

## A1. Prove one `ControlStore` contract in SQLite and memory

Keep one `ControlStore` protocol and make `SqliteJournal` and
`InMemoryControlStore` pass the same parametrized contract suite. The suite must
exercise real contention rather than calling implementations serially:

- same actor/operation/key/request, different owners: one claim and one
  `in_progress` result;
- same actor/operation/key/request, same owner from two concurrent calls: one
  claim and one `in_progress` result;
- same key with a different canonical request: conflict and no new command;
- an unexpired prepared command cannot be reclaimed, regardless of owner id;
- two contenders at an expired claim barrier produce exactly one owner at the next
  epoch and one `in_progress` result;
- an old epoch cannot store a plan, approval, or terminal response;
- a plan is write-once; canonical-JSON-equivalent repetition is idempotent and
  contradiction is damage;
- committed and rejected terminal responses are each write-once; identical
  repetition is idempotent and contradiction is damage;
- approvals are command-bound and write-once; and
- bounded committed-command reads enforce operation/state filtering, an empty or
  operation-scoped high-water key across all command states, deterministic
  keyset order (including tied timestamps), exclusive continuation, inclusive
  `through`, and a positive limit.

The in-memory implementation keeps its real synchronization. It is the I6 second
consumer of the contract, not a looser fake. SQLite additionally proves that
close/reopen preserves the same canonical command models and committed-command
page results.

The bounded committed-command read is added to `ControlStore` for one concrete
recovery consumer:

```python
CommandKey = tuple[str, str]  # created_at ISO-8601, command_id

def latest_command_key(self, *, operation: str) -> CommandKey | None: ...

def committed_commands(
    self,
    *,
    operation: str,
    after: CommandKey | None,
    through: CommandKey,
    limit: PositiveInt,
) -> tuple[CommandRecord, ...]: ...
```

It returns only `state="committed"` rows with non-null `completed_at`, ordered by
immutable `(created_at, command_id)`, strictly after `after` and at or before the
inclusive `through`, up to `limit`. `latest_command_key()` captures the current
high-water key across all rows for that operation, regardless of state, solely to
make one pass finite. It is not a terminal-membership snapshot: a prepared row
behind the cursor may commit later, and a concurrently inserted row may sort on
either side because clocks can tie or move.

The RunHost recovery pump therefore performs repeated mutation-tolerant cycles.
Each cycle captures `through`, advances a keyset cursor for at most a configured
finite number of pages per pump tick, retains progress across ticks, and resets to
`after=None` after reaching/emptying the bound. A row committed behind the cursor
is found in a later cycle. Duplicate discovery is harmless because the command
fence, event receipt, and RunHost intent coalesce. A positive page size is not the
only bound: page count per tick and retry interval are both pinned/tested so an
adversarial store that appends on every read cannot block startup or spin.

The private committed-resume source is injected into RunHost's existing recovery
pump; it does not create a second background scheduler or coroutine owner.
`ControlPlane.startup()` waits for one finite pump tick and continued cycles give
eventual redelivery across concurrent control processes. These methods are not a
transport search API and add no schema/index migration.

Here “concurrent control processes” means the topology the existing SQLite
leases already fence: two independently assembled ControlPlane/RunHost instances
open one shared database. It does not add remote dispatch or a distributed worker
queue. A credential-free two-instance test queues the handoff and commits its
response in one control process, loses that process before worker claim or the
durable attempt-transition receipt, and proves the other process's periodic scan
reconstructs the lost process-local intent. A second lane lets both hosts accept
same-baseline local intents and proves the journal admits one attempt
transition/owner while the losing host follows the existing ownership-loss path.

## A2. Introduce one typed, non-extensible command session

Add a private `_CommandSession` inside the existing control implementation before
moving responsibilities between modules. It owns the one command law:

```text
authorize
→ canonicalize and claim
→ return replay, in-progress, or conflict
→ validate or store one immutable typed plan
→ apply or reconcile the operation-specific fact
→ complete or reject through one terminal path
→ return
```

New plans use one exact private envelope:

```python
class _StoredPlan(BaseModel):
    model_config = ConfigDict(frozen=True, extra="forbid", strict=True)

    schema_version: Literal[1] = 1
    plan: Annotated[_CommandPlan, Field(discriminator="kind")]
```

Every plan variant is also frozen and strict with `extra="forbid"` and an exact
literal `kind`; no permissive base model weakens the envelope.

Outer strictness does not harden an embedded historical L0 model whose own
Pydantic config permits coercion or ignores extras. Therefore every new
schema-1 envelope must also pass one lossless check after parsing:

```text
canonical_json(raw_plan) == canonical_json(parsed_plan.model_dump(mode="json"))
```

Any nested extra, coercion, omitted-default expansion, or lossy normalization is
`JournalDamaged`. New plans are always emitted from the typed model, so their raw
form passes by construction. Operation-specific legacy adapters remain explicit
and byte-preserving; they do not masquerade an unversioned historical shape as a
new envelope or rewrite it to satisfy this check. This single gate avoids
silently changing the accepted parsing behavior of shared frozen L0 contracts.

The closed plan family contains no generic operation registry or extension hook:

```text
_RunCreationPlan     run_id + manifest + inputs + origin + optional source lock
_CancelPlan          run_id + observed status + exact response outcome/status
_ResumePlan          run_id + baseline_event_seq + submitted status; kind binds resume-v1 policy
_ApprovalPlan        exact ApprovalRecord
_RegistrationPlan    definition + content hash + candidate timestamp + row origin
_InitialPromotionPlan component + no-pointer baseline + target + policy draft/id
_PromotionPlan       component + baseline + target + attestation id
_RollbackPlan        component + baseline + target + rollback draft/id
_AdmissionRejectPlan command id + runs_start + request hash + exact AdmissionRejected v1
_ControlRejectPlan   command id + operation + request hash + exact ControlRejected v3
```

`_RunCreationPlan` is shared by start, reproduce, and counterfactual only because
they persist the same domain fact. Counterfactual origin still pins source,
overrides, simulated effect mode, and discard capability mode. Its optional
source lock is absent for start and exact for reproduce/counterfactual: source
`RunId`, manifest/input/source-graph hashes, and the counterfactual
`ResolutionLock` where applicable.

Remove `_object`, `_string`, `_optional_digest`, and other ad hoc durable-plan
parsers. The SQLite column remains generic canonical JSON; the owning operation
validates it through its one exact model.

Compatibility is literal:

- an unversioned historical prepared plan is decoded through an
  operation-specific legacy adapter;
- v1 and v2 committed responses are decoded and returned through the current
  response model;
- neither plan nor response is rewritten during replay;
- malformed or contradictory durable data raises `JournalDamaged`; it is never
  repaired or guessed; and
- existing replay-upgrade fixtures retain canonical stored JSON exactly.

Typed parsing is followed by relational validation against the claimed command
and canonical request. Tests corrupt one field at a time and require damage for:

- wrong plan kind for `CommandRecord.operation`, unknown schema/kind, or outer
  and nested extra/coerced fields;
- a newly created `_RunCreationPlan.run_id` or `_ApprovalPlan.approval_id` not
  derived from the claimed command;
- a cancel/resume/approval target `RunId` that differs from the canonical
  request;
- origin kind, actor, command id, source run, overrides, effect mode, or
  capability mode that differs from the request;
- a run-creation manifest that fails version-aware identity validation equivalent
  to `parse_manifest_json()`, inputs whose canonical hash differs from
  `manifest.input_hash`, or a start source graph/hash that differs from the
  canonical request;
- a reproduce/counterfactual source lock, source graph, source manifest/input
  hash, override set, or resolved pins that differs from the request and immutable
  source run;
- a registration definition/content hash/candidate timestamp or row origin
  that differs from the canonical request, claimed operation, canonical identity
  law, command timestamp, or one exact existing row;
- an initial-promotion edge, policy draft, or deterministic attestation id that
  differs from the request or no-pointer bootstrap policy;
- a promotion edge or attestation that differs from the request; and
- a rollback target, draft, id, or baseline that does not form the planned edge.

Corruption fixtures add nested extras and scalar coercions inside a manifest,
component definition, `AttestationDraft`/check/subject, origin, and approval.
Each must fail the lossless gate before apply; policy-draft extras can never be
dropped and then legitimized by recomputing an id from the reduced model.

The two terminal variants stay explicit because `AdmissionRejected` and
`ControlRejected` deliberately belong to different schema families. Their stored
typed rejection must equal the terminal rejected response, and their command id,
operation, and canonical request hash must equal the claimed `CommandRecord`; a
family, command, operation, request, or payload mismatch is damage. No union
guesses from the shared `status="rejected"` value. Corruption fixtures transplant
an otherwise type-valid plan/response pair across commands, operations, and
same-operation different requests and require refusal; admission rejection is
request-bound because its graph/proposal fields do not bind run inputs.

Authorization failure, invalid request/key, idempotency conflict, and
`in_progress` occur before a command is owned and must not create or modify a
command. A deterministic post-claim refusal that occurs before an operation plan
exists stores the applicable `_AdmissionRejectPlan` or `_ControlRejectPlan`, fires
`after_plan` only after that first durable insert, and then rejects through the
common terminal helper. A refusal
discovered while applying or reconciling an existing `_ResumePlan`,
`_InitialPromotionPlan`, `_PromotionPlan`, or `_RollbackPlan` preserves that
write-once plan and stores the exact rejected response. Successful and rejected
terminal outcomes both fire `after_command_completion` only after their terminal
store commit.

Successful terminal responses receive the same relational scrutiny as plans.
After current-model parsing or an explicit legacy adapter, validate every decoded
response against the claim, typed plan, and immutable domain receipt before
returning it. A response belonging to a new typed-envelope command also passes
the same lossless raw-to-model canonical round-trip before relational validation;
legacy response adapters remain explicit and do not rewrite stored bytes.

- every `CommandMeta.command_id` equals the claim; the stored value has
  `replayed=False`, and only the detached in-memory replay copy flips it to true;
- start, reproduce, and counterfactual submissions carry the planned `RunId`,
  exact origin, and `PENDING`; resume carries its planned `RunId`, origin, and
  planned submitted status;
- cancellation carries the planned `RunId`, outcome, and response status;
- approval carries the exact planned approval id/decision and a detail reference
  derived from that immutable record;
- registration carries the planned component/content hash and a detail reference
  derived from the exact stored version; and
- initial promotion, evaluated promotion, and rollback carry their operation's
  exact status, full planned edge, and detail reference derived from the exact
  attestation/receipt.

Type-valid disagreement is `JournalDamaged`, never replayed. A table-driven suite
changes one relational field at a time for each of all ten operations. The
committed-resume recovery checks remain the stronger attempt-specific subset of
this general response matrix.

## A3. Make reconciliation identities exact

Each command operation has one named fact and one reconciliation rule:

| Operation | Planned fact | Apply/reconcile identity |
| --- | --- | --- |
| `runs_start` | prepared run | deterministic `RunId` derived from `CommandId`; exact manifest, inputs, and origin |
| `runs_cancel` | run-scoped cancellation intent | the planned `RunId` and the journal's durable cancel state; terminal runs are reported without inventing cancellation |
| `runs_resume` | attempt-bound local launch intent | planned `RunId` and `baseline_event_seq` under the resume-v1 status policy, plus the command-bound run-attempt event receipt described below |
| `runs_reproduce` | prepared live clone | deterministic `RunId` plus exact source manifest, inputs, and live origin |
| `runs_counterfactual` | prepared simulated clone | deterministic `RunId` plus exact source lock, overrides, simulated identity, and discard origin |
| `runs_approve` | immutable approval | deterministic `ApprovalId` and exact `ApprovalRecord` |
| `registry_register` | immutable registered version | planned definition/content hash; the first matching row's timestamp is observational, fresh planning proves a restart-stable reference resolves exactly on this host, and replay requires no process-local object |
| `registry_promote_initial` | no-pointer bootstrap promotion | exact deterministic bootstrap policy attestation and `{component, None, target}` edge |
| `registry_promote` | evaluated stable-pointer move | planned attestation id and exact `{component, baseline, target}` edge |
| `registry_rollback` | policy-attested stable-pointer move | planned rollback attestation id and exact `{component, baseline, target}` edge |

Resume remains a process-local hosting request, not a second durable scheduler.
Its apply seam is the attempt-bound handoff to `RunHost`; the handoff precedes
terminal command completion and `RunHost` coalesces an identical queued intent.
Operation-owned replay follow-up is mandatory only where the stored command also
requests process-local hosting: start/reproduce/counterfactual rehost only
still-recoverable prepared rows, and resume reapplies only its stored fence.
`_CommandSession` may decode those responses but must not return so early that
their follow-up is skipped. Registration has no replay follow-up; its stored
response names only the durable row, and later activation cold-binds the recorded
Python reference.

The private handoff result distinguishes `queued`, `coalesced_exact`, and
`superseded`; a Boolean cannot tell an idempotent same-command retry from a
different command at the same fence. Exact coalescence requires run id, baseline,
allowed-status policy, and optional `resume_command_id` all to match. At one
baseline the first different command already retained by that RunHost wins; a
higher baseline may supersede an older queued intent. A still-prepared command
completes successfully only for `queued`/`coalesced_exact` and uses the pinned
`RUN_NOT_RESUMABLE` rejection for `superseded`. Separate processes may each
accept a local handoff, but the journal event fence still permits only one
attempt-transition receipt.

Make resume reconciliation exact by carrying the claimed `command_id` as optional
metadata on the process-local `_LaunchIntent` and into the first successful
attempt event. An explicit resume writes `resume_command_id` in the payload of its
`RunStarted`, `RunResumed`, or `RunReclaimed` event as appropriate. Ordinary
recovery leaves the field absent. This is truthful event provenance, not another
run identity or scheduler. A retry attributes an advanced baseline to this
command only when an event after the baseline carries that exact id.

A committed resume response must survive loss of its process-local handoff. The
RunHost recovery pump therefore performs the mutation-tolerant keyset cycles over
committed `runs_resume` commands through `ControlStore`, and ControlPlane startup
awaits its first finite tick. Before redelivery it
validates the committed response type, command id, response `RunId`, plan `RunId`,
request `RunId`, and fence relationship. It skips unfenced committed legacy plans
for FAILED/PARKED and re-enqueues only an exact unconsumed fence:

- an event after the baseline carries this exact `resume_command_id`: the handoff
  produced its durable attempt receipt, so do not launch again;
- `current_event_seq == baseline_event_seq` and current status is in
  `{PENDING, RUNNING, FAILED, PARKED}`: queue the exact intent; RunHost ownership
  and lease timing still decide when a worker can start;
- `current_event_seq > baseline_event_seq` or status is no longer eligible: the
  old intent is superseded/ineligible and is not revived or falsely credited to
  this command;
- `current_event_seq < baseline_event_seq`: durable damage; and
- identical intents from replay/startup coalesce without another worker.

A reclaimed **prepared** `_ResumePlan` uses the same evidence before it can store
a terminal response. An exact command-bound attempt receipt completes the
original success; an unchanged eligible baseline requeues the exact intent. If
the baseline advanced without that receipt, or the run became ineligible, the
command is terminally rejected through the common completion path with the
existing `RUN_NOT_RESUMABLE` code and an exact
`attempt_superseded`/`status_ineligible` reason. It is never credited with another
command's or ordinary recovery's attempt. A two-command same-baseline race pins
that at most one command-bound receipt exists, competing handoffs yield one
attempt, and any still-prepared loser replays its exact superseded rejection.

The scan is bounded and reconstructs delivery from committed commands; it is not
a durable scheduler or a second run state machine. A crash after handoff but
before command completion leaves a prepared command for caller retry. A crash
after command completion is covered by startup redelivery.

Legacy resume behavior is deliberately asymmetric:

- an unversioned prepared resume plan without a fence cannot be upgraded without
  violating write-once planning and is terminally rejected with
  `RUN_NOT_RESUMABLE` plus reason `attempt_fence_missing`; repair is a new resume
  command/key that stores a current fence before handoff;
- an unversioned committed plan without a fence may recover only PENDING or
  lost-RUNNING work through ordinary RunHost recovery and must never revive
  FAILED/PARKED;
- an unversioned baseline-bearing PR #9 plan uses its persisted fence; and
- a versioned `_ResumePlan` missing `baseline_event_seq` is `JournalDamaged`.

Fixtures cover prepared legacy unfenced rejection/replay, committed unfenced
FAILED/PARKED non-launch, and an unversioned baseline-bearing PR #9 plan surviving
completion, lost handoff, restart, and eventual command-bound attempt receipt.

The committed-resume recovery suite is adversarial rather than a one-row happy
path. It pins:

- more commands than one page, including identical `created_at` values ordered by
  `command_id`, exclusive continuation, and the inclusive finite `through` bound;
- a fake store that appends on every page read, proving one pump tick remains
  finite;
- commands inserted or completed before the cursor, after the cursor, and around
  cycle rollover, proving a later cycle finds rows missed by the current bound;
- a handoff followed by committed response delivery and then process death before
  worker claim/attempt receipt, with recovery occurring without a client retry;
- duplicate discoveries and duplicate commands for one fence coalescing to one
  attempt, plus older/newer fences completing out of order without reviving the
  older intent;
- request/plan/response `RunId` or command-id disagreement, a current sequence
  below the stored baseline, and corruption first encountered on a later page as
  `JournalDamaged`/observable pump failure rather than guessed recovery;
- current status outside the pinned resume-v1 set as non-launch; and
- committed unfenced legacy FAILED/PARKED rows as non-launch while ordinary
  PENDING/lost-RUNNING recovery remains available independently.

First close a latent canonicalization hole instead of building command semantics
on it. `ComponentMetadata.labels` and `LearningProfile.change_surfaces` are sets,
but their current JSON list order varies with `PYTHONHASHSEED`. Make their L0 model
serializers sort those fields. That ordinary `ComponentDef` serialization becomes
the one owner used by new durable rows, content hashing, command request/plan
bytes, registry snapshot digests, and detail output; remove the duplicate
API-detail sorter. This is not a second component representation.

Historical `StoredVersion` rows and hashes remain authoritative and are never
rewritten. The registry-owned pure registration planner searches for an exact
semantic definition before computing a new hash. Exactly one matching historical
row is reused byte-for-byte as `row_origin="existing"`; more than one
matching row with different hashes is damage rather than an arbitrary choice. If
none exists, the planner uses the corrected canonical content hash and the
claimed command's `created_at` to produce one candidate `StoredVersion` with
`row_origin="canonical_new"`. This naming remains truthful when a later command
finds a row already created by PR A; “existing” does not pretend every reuse is
legacy. Recovery validates that an existing row still
exists; that origin is reconcile-only and never feeds historical definition bytes
back through `store_version`. It never recreates a vanished legacy identity.
Cross-process fixtures vary
`PYTHONHASHSEED` and prove equal definitions produce equal request hashes, plan
bytes, new content hashes, detail bytes, and snapshot digests while old rows stay
byte-identical.

Local assembly then obeys the same command law without pretending a Python
callable is durable JSON. `registry_register` normalizes a `DefinitionBundle` to
its strict `ComponentDef`; only that canonical definition is the request. After
authorization, lifecycle admission, canonicalization, and claim, a fresh command
calls the registry-owned pure planner. For an atomic definition the planner
requires a restart-stable module spec/loader, resolves
`PythonRef.module:qualname` on the current host, rejects `__main__`,
local/non-restartable, missing, or non-callable targets, requires the resolved
object to be the bundle's implementation when one was supplied, and validates
the declared source digest and port-contract hash. A same-source callable under
the wrong module is refused. Fresh-process tests, rather than an already-loaded

Lifecycle semantics are pinned:

- synchronize `new → starting → started → stopping → stopped` under one lifecycle
  lock, with shared startup/shutdown tasks and an admitted-mutation count;
- `startup()` and every mutation arriving in `new` create or join the same full
  startup task. That task starts the RunHost pump, awaits one finite durable-run
  refill tick, and awaits one finite committed-resume keyset tick; later pump ticks

- a mutation arriving during `starting` awaits the shared startup result through
  `asyncio.shield` (or equivalent), then re-enters the lifecycle lock. It is
  admitted and increments the active count only if state is still `started` and
  closing is false. If shutdown won that lock, it raises `ControlPlaneClosed`

- concurrent startup callers observe the same original success or failure. One
  cancelled waiter cannot cancel the shared startup task. After a failed startup,

  orchestration scope

- startup racing shutdown finishes or fails once. A mutation merely waiting on

  command. The one shutdown path then reaches `stopped`.

  is within the exact materialized collection;

  digest still matches, `0 <= offset <= total_bytes`, and the offset is zero, end,
  or an actual UTF-8 code-point boundary; and
- all endpoints reject negative, reversed, future, wrong-shaped, or out-of-range
  bounds with typed `CURSOR_INVALID` and no payload.

Add tests for malformed base64/JSON, unknown fields, schema 1, schema 3, corrupted
checksum, wrong actor/kind/query, negative/reversed bounds, future store bounds,
offsets beyond the exact collection, and booleans in integer fields (Python
`bool` must not pass as `int`). Run-bound validation proves only that the cursor is
coherent in the global append-only key domain; it does not claim to snapshot
mutable run-status membership.

Add a forged detail cursor whose offset lands inside a multibyte character. It
must return `CURSOR_INVALID`, not an empty chunk or a same-offset continuation;
every accepted nonterminal detail cursor makes positive byte progress.

## B4. Replace private walker reach-through with explicit runtime methods

Promote only the runtime operations already required by L4:

```python
Walker.load_manifest(run_id) -> ExecutionManifest
Walker.materialize_run(run_id) -> dict[str, Any]
```

`materialize_run()` loads recorded inputs internally, validates the recorded
manifest through the existing compatibility path, and materializes only from
durable checkpoints. `Constructicon.manifest_for_run()` and
`Constructicon.materialize_run()` delegate to these methods. No control-layer
code interprets graph structure or checkpoints.

Tests cover current and historical manifests, successful atomic and loop results,
missing inputs, missing/damaged/contradictory checkpoints, and identical canonical
result/detail JSON before and after the boundary change. A source search must find
no L4 call to walker methods beginning `_load_manifest` or `_materialize`.

# Final elegance test

The phase is complete only when these statements are literally true:

> A transport derives one actor and delegates a mutation once. `ControlPlane`
> authorizes it, opens one fenced command session, validates one typed immutable
> plan, applies or reconciles one exact fact, and stores one terminal response.

> Trusted local assembly supplies a launcher-minted static actor and caller key to
> that same `ControlPlane`. Registration and initial promotion have durable plans
> and receipts but no transport route; `Constructicon` exposes no mutation bypass.

> A component definition has one canonical serializer. A durable registration
> names one exact stored version; process-local callables and caches can neither
> change replay nor become recovery authority.

> A registry cursor names one exact captured vector cut. New registration or
> promotion is visible to a new query and cannot change any page sequence already
> started.

> `ControlPlane` owns lifecycle and delegates by responsibility. `RunHost` owns
> bounded local coroutines. The walker alone schedules graph units and
> materializes durable execution state.

> `SqliteJournal` is one concrete store at schema version 5. Its private files are
> named for enduring responsibilities, and moving them changes no logical schema,
> row value, fence, transaction, probe, or identity.

> M6 is marked done only after the protected exact `main` commit proves all of the
> above. M7 then begins from that commit, not from historical intent.
